## Bối cảnh

S§13.2–§13.3, §14.3, ADR-0022 và ADR-0027 mô tả webhook vào, `http_request`/`run_n8n_workflow`, chữ ký Standard Webhooks và token causation nhưng chưa có code (`main` `92327742`: chỉ có prefix `hok` và tên event). S5b để lại năm việc cho gói này (S5b-review §11 #1–#5): (1) giao Telegram/email đang giữ transaction qua lời gọi mạng — HTTP ra phải tách "nhận việc" khỏi "gọi mạng" ngay từ đầu; (2) nhịp gửi theo đích + `Retry-After`; (3) mỗi webhook vào sinh ghi **đơn lẻ** nên `record.assigned`/`record.followed_changed` không được gom (ADR-0026 §2 chỉ gom ghi hàng loạt) — một nguồn bắn 1.000 request/phút tạo 1.000 thông báo + thư; (4) poller Telegram chỉ chạy khi có link chờ nên `/stop` chậm (QA S5b M4); (5) câu trả lời của poller không qua bucket của bot (M5).

Thêm một xung đột trong tài liệu đã Accepted: ADR-0026 §5 đếm đơn vị kích hoạt của `webhook.received` theo **từng request** và tắt automation khi > 100 đơn vị/phút, trong khi S§13.2 cho mỗi hook mặc định 5 req/s (300/phút). Một tích hợp hợp lệ 2 req/s sẽ làm automation tự tắt.

Quy mô (S5c-research §3): self-host, trần cứng 20 req/s/IP, 5–50 req/s/hook, 50 req/s/base → ≤ 150 ghi Postgres/giây ở trần: "small". Không thêm hạ tầng (quy tắc vàng #7): Postgres + Valkey + graphile-worker.

```text
                 ┌────────────── API (Fastify) ──────────────┐
 bên gửi ──POST /api/v1/hooks/:token──► IP limit → tra token (cross-tenant, chỉ org+id)
                 │  → bucket hook/base (Valkey Lua) → body ≤ 1 MB → Bearer / Standard Webhooks
                 │  → TX: incoming_webhook_requests (UNIQUE message_id) + meta.events webhook.received
                 │        + job events.dispatch (+ mẫu nếu đang nghe) → 202
                 └────────────────────────────────────────────┘
 worker: events.dispatch → loop guard (causation) → run automation.run
         automation.run bước http_request: TX pha 1: bước waiting + http_deliveries pending + job http.deliver
         http.deliver: TX nhận lease → commit → bucket (org,host) → net guard (resolve, ghim IP, không redirect)
                       → gọi đích (10 s, ≤ 1 MB) → TX pha 2: kết quả / hẹn thử lại → đánh thức automation.run
 Telegram ──POST /api/v1/telegram/webhook/:pathToken (secret header)──► TX xử lý /start,/stop → job trả lời qua bucket bot → 200
```

## Quyết định

### 1. Webhook vào

- **Mô hình** (`meta.incoming_webhooks`, sửa dòng S§5.10): `id 'hok_'`, `organization_id`, `base_id`, `name` (1–100, duy nhất trong base không phân biệt hoa thường), `token_hash` (sha256 hex, `UNIQUE` toàn instance — tra cứu vượt tenant), `token_enc` (AES-256-GCM, HKDF `info = incoming-webhook:v1`; để base admin xem lại URL — **khác** chữ "lưu hash" của S§13.2: URL phải dán lại nhiều lần vào hệ khác, đổi token làm gãy tích hợp; vẫn tra bằng hash, xem URL cần quyền quản lý), `signing_secret_enc` NULL + `signing_secret_prev_enc` NULL + `signing_secret_prev_expires_at` NULL (xoay 24 h — ADR-0022 §3), `bearer_hash` NULL, `rate_limit_per_sec` (1…`WEBHOOK_MAX_RATE_PER_SEC`, mặc định 5, burst 4×), `listen_until` NULL, `listened_by` NULL, `sample` jsonb NULL, `sample_captured_at` NULL, `enabled`, `created_by`, `created_at`, `updated_at`, `deleted_at` NULL. Bỏ cột `target` của S§5.10 (automation tham chiếu hook, không phải ngược lại). FK ghép `(organization_id, base_id)` → `bases` `CASCADE`. ≤ 50 hook mỗi base.
- **Quyền**: quản lý hook (tạo/sửa/xoá/xoay/nghe/xem log/xem URL) **chỉ base admin** (hook không gắn table, payload có thể ghi vào bất kỳ table nào qua automation; như trigger `schedule` — ADR-0025 §3). Đọc được base mà không phải base admin → `403`; không đọc được base, org khác → `404`.
- **Bí mật hiển thị một lần**: secret ký `whsec_<base64 32 byte>` (sinh ở server) và Bearer token (32 byte base64url) chỉ có trong response tạo/xoay; không có endpoint đọc lại.
- **Route công khai** `POST /api/v1/hooks/:token` (chỉ `POST`; có trong OpenAPI), theo thứ tự, mỗi bước rẻ hơn bước sau: (1) giới hạn 20 req/s/IP sẵn có (S§13.1); (2) token sai định dạng → `404`; (3) tra `token_hash` qua tra cứu vượt tenant `findIncomingWebhookByTokenHash` (chỉ org id + hook id, S§14.1) rồi đọc hook bằng repository có `organizationId`; không có, tắt, đã xoá, base trong thùng rác → `404` (cùng một câu trả lời); (4) bucket theo hook (`rate_limit_per_sec`, burst 4×) + trần 50 req/s/base, script Lua nguyên tử → `429 RATE_LIMITED` + `Retry-After`; Valkey không sẵn sàng → `503 DEPENDENCY_UNAVAILABLE` + `Retry-After: 1` (fail-closed: bên gửi webhook tự thử lại); (5) đọc body thô ≤ 1 MiB (`413 PAYLOAD_TOO_LARGE`, dừng đọc ngay khi vượt); `Content-Type` `application/json` (đối tượng hoặc mảng) hoặc `application/x-www-form-urlencoded` (thành đối tượng, khoá lặp → mảng), body rỗng = `null`, khác → `415 UNSUPPORTED_MEDIA_TYPE`, JSON hỏng → `400 BAD_REQUEST`; (6) Bearer (nếu bật) rồi Standard Webhooks (nếu có secret): timestamp lệch ≤ 300 s, chữ ký `v1` khớp secret hiện tại **hoặc** secret cũ còn hạn, so constant-time; sai/thiếu → `401 UNAUTHENTICATED` không nói lý do (C§10); (7) **một transaction**: chèn `meta.incoming_webhook_requests` (`ON CONFLICT (organization_id, incoming_webhook_id, message_id) DO NOTHING` — trùng → `202`, không event), event `webhook.received` (payload chỉ id: `incoming_webhook_id`, `request_id`; `actor = { type: webhook, id: hok_… }`; `causation` từ §5), job `events.dispatch`, lưu mẫu nếu đang nghe; (8) `202 { "request_id": "whr_…" }`. Không chạy automation trong request (skill `form-collector.md`).
- **Dòng request thô** `meta.incoming_webhook_requests`: `id 'whr_'`, `organization_id`, `incoming_webhook_id`, `message_id` NULL (`webhook-id` khi hook có secret — dedupe; không secret thì `NULL`, không dedupe), `received_at`, `body` jsonb, `headers` jsonb (tên viết thường, ≤ 50 header × 8 KB, **đã bỏ** `authorization`, `cookie`, `webhook-signature`, `x-cellhive-causation`, `x-telegram-bot-api-secret-token`), `query` jsonb, `size_bytes`, `causation_accepted` boolean, `event_id`. Giữ **7 ngày** (cron dọn qua `purgeExpiredOperationalRows`); chống replay vì vậy rộng hơn "24 h" của C§10 (đúng hơn, không hẹp hơn). Run đọc dữ liệu trigger từ dòng này; dòng đã dọn → bước dùng `{ trigger: … }` của run chạy lại lỗi `trigger_data_expired`. Log request cho base admin (`GET …/incoming-webhooks/:id/requests`, chỉ siêu dữ liệu: thời điểm, kích thước, kết quả, event id — body chỉ ở mẫu và chi tiết run).
- **Nghe request mẫu** (S§11.4): `POST …/incoming-webhooks/:id/listen` đặt `listen_until = now + 180 s`, xoá mẫu cũ; request **hợp lệ** đầu tiên (sau bước 6) trong cửa sổ được lưu vào `sample` (body ≤ 64 KB, cắt thì `sample.truncated = true`; header đã lọc như trên) và kết thúc cửa sổ; người nghe nhận envelope realtime `incoming_webhook.sample_captured` trên kênh `user:` (chỉ id), FE refetch khi focus lại làm dự phòng. Request mẫu **vẫn được xử lý bình thường** (giữ S§11.4; khác URL test của n8n — UI ghi rõ). Tối đa một cửa sổ nghe mỗi hook (nghe lại thay cửa sổ cũ).
- **Audit** (C§8): `incoming_webhook.created|updated|deleted` (đã có tên), thêm `incoming_webhook.secret_rotated`, `incoming_webhook.token_regenerated` — chỉ cấu hình, không bao giờ token/secret/body.

### 2. Trigger `webhook.received` và giá trị

`webhook.received { incoming_webhook_id }` — hook chưa xoá của **cùng base** (`UNKNOWN_WEBHOOK`); quản lý automation có trigger này: chỉ base admin. Dispatch: event `webhook.received` → automation đang bật nghe đúng hook; không `condition` trên record (trigger không có record — `condition` phải `null`, `INVALID_CONDITION`); `input.trigger = { type, event_id, incoming_webhook_id, request_id }`. Giá trị `{ "trigger": "body" | "headers" | "query", "path" }` và tham chiếu template `[@body.<path>]`… theo S§11.4 (header nhạy cảm không bao giờ đọc được). Dữ liệu ngoài vào template là text node (đã an toàn sẵn, T504). Mảng JSON ở gốc body là **một** request, một run (khác Zapier).

### 3. Lõi mạng ra chống SSRF (`packages/server-core/src/net/**`)

- Một client cho mọi gọi HTTP ra của server (`http_request`, `run_n8n_workflow`, Telegram webhook dùng `TelegramClient` có host cố định nên không cần): `node:http`/`node:https` với tuỳ chọn `lookup` trả **đúng** địa chỉ đã kiểm (ghim IP, chống DNS rebinding), `servername`/`Host` giữ tên host gốc, TLS kiểm chứng chỉ. **Không thêm dependency** (không `undici`, không `standardwebhooks`).
- URL: chỉ `http`/`https`, không userinfo, không IPv6 zone id, host IDN chuẩn hoá punycode; cổng 80/443 hoặc cổng nêu trong mục allowlist khớp. Resolve **một lần** lấy **mọi** địa chỉ (A + AAAA); có một địa chỉ bị chặn → từ chối cả host (trừ khi host khớp allowlist), nối tới địa chỉ đầu tiên được phép. IP literal trong URL kiểm như địa chỉ đã resolve; IPv4-mapped IPv6 kiểm theo IPv4.
- Phân loại địa chỉ dùng chung với SMTP (`classifyAddress` chuyển từ `mail/identities/host-guard.ts` sang `net/address-class.ts`, giữ re-export): **chặn** loopback, RFC1918, link-local (gồm metadata), CGNAT, ULA, multicast, không xác định, dành riêng, tài liệu/benchmark. **Không bao giờ mở được** (kể cả allowlist): `0.0.0.0/8`, `::`, multicast, broadcast, metadata cloud (`169.254.169.254`, `fd00:ec2::254`, `100.100.100.200`).
- **Allowlist theo org** `meta.http_allowlist (id 'hal_', organization_id, pattern, note, created_by, created_at)` — pattern = host chính xác hoặc `*.hậu_tố` (≥ 2 nhãn), tuỳ chọn `:cổng`; IP literal/CIDR **không** nhận (allowlist theo tên — mục đích là "n8n nội bộ"). Khớp → được nối tới địa chỉ private/ULA/CGNAT; **loopback** chỉ khi mục nêu đúng host **và** cổng. Quản lý: org owner/admin (`GET|POST /orgs/:orgId/http-allowlist`, `DELETE /http-allowlist/:id`; người khác `403`, org khác `404`), ≤ 100 mục, audit `http_allowlist.created|deleted`. Env mới `HTTP_PRIVATE_ALLOWLIST` = `org` (mặc định) | `off` — `off` cho instance nhiều org không tin nhau: allowlist không mở được địa chỉ private nào (chỉ cho phép cổng khác 80/443 trên host công khai).
- Không follow redirect (`3xx` trả về như response; bước coi là không thành công — `http_status`). Timeout tổng 10 s (kết nối 5 s), response đọc tối đa 1 MiB rồi huỷ (`http_response_too_large`), không nén lớn hơn trần sau giải nén. Không dùng biến `HTTP(S)_PROXY` (proxy egress là P2). Không log URL đầy đủ (chỉ host), header, body.
- Mã lỗi (bước run, C§21): `ssrf_blocked` (`params.reason`: `private_address` | `blocked_address` | `port_not_allowed` | `invalid_url` | `unresolvable`), `http_timeout`, `http_network`, `http_response_too_large`, `http_status` (`params.status`), `rate_limited` (`params.retry_after_s`).

> **Sửa đổi (2026-10-18, T616)**: metadata cloud không bao giờ mở được gồm cả `169.254.170.2` — xem dòng Sửa đổi cùng ngày đầu ADR.

### 4. HTTP ra qua outbox hai pha

- **Bảng** `meta.http_deliveries`: `id 'hdl_'`, `organization_id`, `kind` `action` | `test`, `automation_id` NULL, `run_id` NULL, `action_id` NULL, `requested_by` NULL (test), `idempotency_key` (= `Idempotency-Key`; `UNIQUE (organization_id, idempotency_key)` cho `action`), `message_id` (= `webhook-id`: `evt_…` của event gốc, run không có event thì `run_…` — giữ qua mọi lần thử, ADR-0022 §2), `method`, `target_host`, `request_enc` (URL + header không bí mật + body đã render, AES-256-GCM HKDF `info = http-delivery:v1`; **xoá** khi tới trạng thái cuối), `auth_secret_id` NULL, `signing_secret_id` NULL, `status` `pending` | `sending` | `succeeded` | `failed` | `cancelled`, `attempts`, `next_attempt_at`, `lease_until` NULL, `last_status` NULL, `last_error` jsonb NULL, `response` jsonb NULL (status, `content-type`, body ≤ 10 KB đã cắt), `created_at`, `completed_at` NULL. FK ghép tới `automation_runs` `CASCADE`; index một phần `(next_attempt_at) WHERE status IN ('pending','sending')`. Giữ theo thời hạn của run (T518); `test` 24 h.
- **Pha 1** (transaction của bước, engine T505): render giá trị bằng quyền `run_as` lúc chạy (ADR-0025), kiểm URL tĩnh (cú pháp, scheme, cổng — SSRF đầy đủ ở pha 2 vì DNS có thể đổi), chèn dòng `pending`, bước `waiting` (output `{ delivery_id }`), run `waiting` như `delay` (không giữ chỗ trần org, không tính 15 phút), job `http.deliver { organization_id, delivery_id }` (`job_key = http:<delivery_id>`). Bước đã có dòng giao (chạy lại job) dùng lại dòng (idempotent).
- **Pha 2** (job `http.deliver`): TX-a khoá dòng `FOR UPDATE SKIP LOCKED`, `pending`/hết lease → `sending`, `attempts + 1`, `lease_until = now + 30 s`, commit — **không** giữ transaction hay kết nối DB trong lúc gọi mạng. Lấy lượt: khoá tạm dừng (org, host) còn hạn hoặc bucket (org, host) hết lượt → hẹn lại job (`run_at`), trả dòng về `pending` không tính lần thử; ≤ 2 lời gọi đang bay mỗi org (semaphore Valkey có lease) để một org có đích chậm không chiếm hết `WORKER_CONCURRENCY`. Giải mã request + secret chỉ trong bộ nhớ, gắn header (§4 dưới), gọi qua lõi §3. TX-b ghi kết quả: thành công (`2xx`) → `succeeded` + bước `succeeded` (output `{ status, headers: { content-type }, body }` — JSON parse nếu là JSON, không thì chuỗi; cắt 10 KB) + enqueue `automation.run`; lỗi tạm → `pending` + `next_attempt_at`; lỗi vĩnh viễn/hết lượt → `failed` + bước `failed` (mã §3) + enqueue `automation.run` (run `failed` theo luật T505 — DLQ = run `failed`, "chạy lại" T518 tạo dòng giao mới).
- **Thử lại**: tối đa 6 lần (ngay, +10 s, +1 phút, +5 phút, +15 phút, +30 phút, jitter ±20 %). Tạm: lỗi mạng, timeout, `408`, `425`, `429`, `500`, `502`, `503`, `504`. Vĩnh viễn: `ssrf_blocked`, `3xx`, `4xx` khác, `501`, `410` (Standard Webhooks: endpoint đã gỡ), `http_response_too_large`. `Retry-After` (giây hoặc ngày HTTP) của `429`/`503` ≤ 1 giờ → lần sau = max(lịch, `Retry-After`) **và** đặt khoá tạm dừng (org, host) tới thời điểm đó (mọi dòng giao khác tới host đó chờ — không bão retry); > 1 giờ → `failed` `rate_limited`. Huỷ run (T518) → dòng `pending` thành `cancelled`; dòng `sending` chạy xong rồi bỏ kết quả.

> **Sửa đổi (2026-10-19, T617)**: lỗi tạm = `408`, `425`, `429`, mọi `5xx` trừ `501`, và `ssrf_blocked` `unresolvable` có `params.cause` `timeout`/`temporary` — xem dòng Sửa đổi cùng ngày đầu ADR.

- **Nhịp theo đích**: bucket Valkey (org, host) 10 lời gọi/giây, burst 20 — dùng lại helper token bucket của `mail/limits.ts` (T541) như `TelegramSendPacers`. Valkey lỗi → hẹn lại, không tính lần thử.
- **Áp lại cho email/Telegram**: S9 (S5b-review §11 #1) — S5c không đổi `notifications.deliver`/`send_email`/`send_telegram`.

### 5. Loop guard qua HTTP

- **Token causation** đúng ADR-0027 (AES-256-GCM, HKDF `info = automation-causation-v1`, `target = sha256(host + path)`, hết hạn 1 h, mỗi lần thử một token mới). Làm rõ phía nhận: `target` khớp khi path **đúng** path request **và** host là host của `PUBLIC_URL` **hoặc** header `Host` sau proxy tin cậy (`TRUSTED_PROXIES`) — token mã hoá nên header `Host` giả không tạo được token; nhờ vậy gọi qua tên service Docker (`api:3000`) vẫn nối chuỗi. Hợp lệ → `causation = { root_event_id, depth + 1, automation_chain }`; sai → bỏ qua header (depth 0), metric `automation_causation_rejected_total`.
- **Đơn vị kích hoạt của `webhook.received`** (sửa ADR-0026 §5 "từng request"): request có causation hợp lệ → `causation.root_event_id` như event nội bộ; không có → `webhook:<hok>:<giây epoch>` (mọi request của một hook trong cùng giây là một đơn vị). Một hook tạo ≤ 60 đơn vị/phút nên không bao giờ tự tắt automation chỉ vì nhịp hợp lệ; luật "50 đơn vị liên tiếp thất bại" vẫn áp; vòng lặp qua trung gian làm rơi header bị chặn bởi bucket của hook (≤ `WEBHOOK_MAX_RATE_PER_SEC`) + luật thất bại liên tiếp + `depth` khi header còn.
- Header ra (C§10): `webhook-id`, `webhook-timestamp`, `webhook-signature` (khi có secret ký; hai chữ ký trong 24 h sau xoay), `Idempotency-Key = <aut>:<event hoặc run>:<act>`, `X-Cellhive-Causation`, `User-Agent: Cellhive/<version>`, `Content-Type` theo body. Header do người dùng đặt không được trùng các tên này, `host`, `content-length`, `connection`, `transfer-encoding`, `te`, `upgrade`, `proxy-*` (`HEADER_NOT_ALLOWED`).

> **Sửa đổi (2026-10-18, T616)**: token causation gắn chính instance (host `PUBLIC_URL` + tiền tố `/api/v1/hooks`), phía nhận kiểm theo tiền tố path hook thay vì path chính xác; `Idempotency-Key` của run không có event dùng `run_id` — xem các dòng Sửa đổi cùng ngày đầu ADR. Nội dung đã Accepted ở trên giữ nguyên.

### 6. Gom thông báo cho ghi từ webhook (S5b-review §11 #3)

- Engine (T505) ghi event của run có trigger `webhook.received` với `via.incoming_webhook_id = hok_…` (thêm vào `via`, dạng như audit).
- `NotificationEventListener` (ADR-0034 §2): event không hàng loạt có `via.incoming_webhook_id` → **luôn qua bộ đệm**, không đi đường đơn lẻ: `record.assigned` → `kind = assigned`, `group_key = webhook:<hok>:<table_id>`, debounce **60 s từ hàng đầu** (`debounce = from_first`); `record.followed_changed` → `kind = followed`, `group_key = webhook:<hok>:<table_id>` cùng debounce (thay vì theo record). Xả: mỗi người nhận **một** thông báo mỗi (hook, table, cửa sổ 60 s); `data` thêm `source = { incoming_webhook_id }` và với `record.followed_changed` thêm `record_ids` (≤ 20) + `record_count` (chỉ record người đó đọc được, field lọc như ADR-0034 §2). Trần tự nhiên: ≤ 60 thông báo mỗi người mỗi giờ cho mỗi (hook, table, loại); email/Telegram theo tuỳ chọn như cũ.
- Đánh đổi: thông báo gán từ webhook đến chậm tối đa 60 s (mốc < 1 s của S5b chỉ cho ghi của người dùng). Ghi hàng loạt từ webhook (run `update_records`) vẫn theo ADR-0026/ADR-0034 (gom theo `batch.id`; người theo dõi không nhận).

### 7. Telegram: chế độ webhook, trả lời qua bucket, poll thưa (S5b-review §11 #4–#5)

- **Chế độ** `organizations.settings.notifications.telegram_delivery_mode` = `polling` (mặc định, như ADR-0034 §3) | `webhook`. `PATCH /orgs/:orgId/notification-channels { telegram_delivery_mode }` (org owner/admin): `webhook` chỉ khi `PUBLIC_URL` là `https` và cổng 443/80/88/8443 (không thì `422` / `PUBLIC_URL_NOT_HTTPS`); server gọi `getWebhookInfo` — bot đang có webhook tới URL khác → `422` / `TELEGRAM_WEBHOOK_CONFLICT` (không bao giờ ghi đè tích hợp khác; người dùng gỡ ở nơi kia); rồi `setWebhook(url, secret_token, allowed_updates = ["message"], max_connections = 10)`; Telegram không trả lời → `503 DEPENDENCY_UNAVAILABLE`. Về `polling` hoặc đổi/bỏ bot → `deleteWebhook` (bot cũ) trong cùng thao tác. Giữ "một bot một org" (`BOT_IN_USE`).
- **Bảng** `meta.telegram_webhooks (organization_id PK, secret_id, path_token_hash UNIQUE, secret_token_enc, registered_url, status ok|error, last_error_code NULL, last_checked_at, created_at, updated_at)` — FK ghép tới `secrets`; `secret_token` 64 ký tự `[A-Za-z0-9_-]` mã hoá HKDF `info = telegram-webhook:v1`. Không đặt trong `meta.secrets` (danh sách đó là secret người dùng quản lý).
- **Route** `POST /api/v1/telegram/webhook/:pathToken` (công khai, không trong OpenAPI công khai vì chỉ Telegram gọi — ghi C§22.7): path token không khớp → `404`; header `X-Telegram-Bot-Api-Secret-Token` sai (constant-time) → `401`; body ≤ 1 MiB JSON; xử lý update bằng **cùng** `TelegramUpdateHandler` của poller (tách khỏi `TelegramLinkPoller`) trong một transaction; trả lời người dùng **không** gửi trong request mà qua job `notifications.telegram_reply` (đi qua `TelegramSendPacers` của bot); `200` cả khi update không liên quan/token link sai (tránh Telegram gửi lại); DB lỗi → `503` (Telegram tự gửi lại). Cron mỗi giờ `getWebhookInfo` cho bot ở chế độ webhook: URL lệch (đổi `PUBLIC_URL`) → đăng ký lại; `last_error_message` → `status = error` hiện trong cài đặt (không log nội dung).
- **Poll thưa** (M4, chế độ `polling`): ngoài poll khi có link chờ, cron mỗi 15 phút poll ngắn (`timeout = 0`, một lượt) cho bot có ≥ 1 kênh `linked` → `/stop` được xử lý ≤ 15 phút. Ở chế độ `webhook`: ngay lập tức.
- **Trả lời qua bucket** (M5): mọi trả lời của poller và webhook đi qua `TelegramSendPacers` (25 tin/giây/bot, 1 tin/giây/chat, chung với `send_telegram` và giao thông báo); trả lời "Link không hợp lệ" tối đa **3 lần mỗi chat mỗi giờ** (Valkey), sau đó im lặng (đổi C§22.7 "mọi `/start` sai cùng một trả lời").

### 8. Secret dùng cho HTTP ra (`meta.secrets`, C§24)

Hai `kind` mới (migration đổi CHECK): `http_header` — giá trị (≤ 4.096, ASCII in được, không CR/LF) là **giá trị** header; tên header nằm trong cấu hình action (vd `Authorization`, `X-Api-Key`); `webhook_signing` — `whsec_<base64 24–64 byte>`, nhận giá trị người dùng dán hoặc `generate: true` (server sinh, trả `value` **một lần** trong `201`). Đổi `value` (`PATCH`) của `webhook_signing` giữ giá trị cũ 24 h (`previous_ciphertext`, `previous_expires_at` — cột mới) để gửi hai chữ ký. Phạm vi base, `usages`, `409 SECRET_IN_USE` như `telegram_bot`. Quản lý: org owner/admin (giữ C§24); base admin tự thêm secret vẫn là P1.

## Phương án đã cân nhắc

| Quyết định | Phương án A (chọn) | Phương án B | Lý do |
|---|---|---|---|
| Gọi HTTP ra | Outbox hai pha + job riêng, run `waiting` | Gọi thẳng trong bước của `automation.run` (giữ transaction/kết nối như email T512) | B làm pool DB + `WORKER_CONCURRENCY` thành nút cổ chai khi đích chậm (S5b I4, L3); A khôi phục được sau crash, retry dài không chiếm run |
| Client HTTP | `node:http(s)` + `lookup` ghim IP, không dependency | `undici` `Agent({ connect: { lookup } })` hoặc thư viện "ssrf-agent" | Không cần thêm gói (quy tắc #7), hành vi kiểm được hết trong repo; dùng lại `classifyAddress` của T530 |
| Redirect | Không follow | Follow ≤ 3 hop, kiểm lại từng hop (S§14.3 cho phép) | Ít bề mặt nhất; đích webhook/n8n không cần redirect |
| Allowlist | Theo tên host của org + env tắt cho instance nhiều org | Env instance dạng CIDR (n8n/Baserow) | S§14.3 định nghĩa allowlist theo org; env `off` giữ an toàn cho instance chia sẻ |
| Dedupe webhook vào | `UNIQUE` trên dòng request Postgres (7 ngày) | Valkey `SET NX` 24 h | Cùng transaction với event (skill: không để kho dedupe lệch dữ liệu); Valkey mất dữ liệu khi restart |
| Body webhook vào | Bảng request riêng, event chỉ id | Body trong `meta.events.payload` | Event giữ "payload chỉ id", bảng events không phình; có thời hạn riêng + log |
| URL hook | Lưu hash (tra) + bản mã hoá (xem lại) | Chỉ hash, hiện một lần (S§13.2) | URL dán vào nhiều hệ; tạo lại làm gãy tích hợp; vẫn chỉ base admin xem |
| Đơn vị breaker của webhook | Cửa sổ 1 giây mỗi hook | Từng request (ADR-0026 §5) | B tự tắt automation ở nhịp hợp lệ 2 req/s |
| Gom thông báo từ webhook | Bộ đệm theo (hook, table), 60 s | Coi ghi từ webhook là hàng loạt (bỏ báo người theo dõi) / ngưỡng nhịp Valkey | Hàng loạt làm mất thông báo người dùng muốn (vd "đã thanh toán"); ngưỡng nhịp phụ thuộc Valkey và khó kiểm thử |
| Telegram webhook | Tuỳ chọn, poll mặc định, không ghi đè webhook khác | Bật tự động khi `PUBLIC_URL` https | Tự động có thể cướp bot đang dùng ở hệ khác; nhiều cài đặt có https nhưng chặn đường vào từ Telegram |
| Secret của hook vào | Cột mã hoá trên hook | `meta.secrets` | Secret do server sinh cho đúng một hook, base admin quản lý; `meta.secrets` là của org admin |
